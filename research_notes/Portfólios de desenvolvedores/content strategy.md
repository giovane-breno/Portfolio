# Estratégia de conteúdo para portfólio de desenvolvedor

## 1. Posicionamento e apresentação da experiência

### Takeaway

O portfólio deve posicionar Giovane como desenvolvedor web full-stack com foco prático em produtos administrativos e SaaS, conectando frontend, backend e entrega. A experiência deve ser escrita como contribuição e resultado verificável — não como lista de responsabilidades ou superlativos.

### Cited Findings

- O GitHub recomenda uma bio de uma ou duas frases, com uma visão geral do profissional e do tipo de trabalho procurado; também recomenda incluir site/portfólio e redes sociais. — [GitHub Docs: Using your GitHub profile to enhance your resume](https://docs.github.com/en/account-and-profile/tutorials/using-your-github-profile-to-enhance-your-resume)
- Para currículo, Harvard recomenda adaptar o conteúdo à vaga, usar verbos de ação, demonstrar impacto/resultados, priorizar concisão e manter a ordem cronológica reversa. — [Harvard FAS: Create impactful resumes and cover letters](https://careerservices.fas.harvard.edu/resources/hes-create-impactful-resumes-and-cover-letters/)
- Em conteúdo web, estudos resumidos pela Nielsen Norman Group encontraram ganhos de usabilidade quando o texto é conciso, escaneável e objetivo; a versão combinada teve 124% de melhora na métrica do estudo. — [Nielsen Norman Group: Concise, Scannable, and Objective](https://www.nngroup.com/articles/concise-scannable-and-objective-how-to-write-for-the-web/)
- O conteúdo local de Giovane já informa: freelancer autônomo desde outubro de 2025; Analista de Suporte Técnico I na COE de março de 2024 a outubro de 2025; suporte N1 na Câmara Municipal de São José dos Campos de março a dezembro de 2023; suporte N1 na Prefeitura de São José dos Campos de agosto de 2022 a janeiro de 2023; e Fullstack Developer na Casa de Ração Jardim Sul de março de 2021 a julho de 2022. — [Base local consultada: `index.html`](../../index.html)
- O mesmo conteúdo local descreve automação e suporte a Active Directory/infraestrutura hospitalar na COE e um ERP/PDV em produção real na Casa de Ração Jardim Sul. Esses itens são bons pontos de diferenciação porque mostram contexto operacional, não apenas tecnologias. — [Base local consultada: `index.html`](../../index.html)

### Inferences

- A headline recomendada é específica e sóbria: “Desenvolvedor full-stack focado em aplicações web, APIs e produtos administrativos” ou “Desenvolvedor full-stack com experiência em Laravel, React/Vue e entrega de aplicações web”. Isso é mais defensável que “arquiteto”, “especialista” ou “construo produtos SaaS do zero” quando não há métricas, escopo ou links que provem cada afirmação.
- Organizar a experiência em duas camadas ajuda: (1) experiência de desenvolvimento: Casa de Ração e freelancer; (2) experiência de suporte/infraestrutura: COE, Câmara e Prefeitura. A segunda camada não deve ser escondida: ela sustenta comunicação com usuários, diagnóstico, operação e visão de produção.
- Para cada cargo, usar no máximo 2–3 bullets no formato “ação + contexto + resultado/evidência”. Se não houver métrica, usar evidência qualitativa honesta: “entregue em produção”, “usado por equipe interna”, “integração com sistema MV” ou “reduziu trabalho manual”, desde que Giovane confirme.

### Gaps

- Não há, no conteúdo local consultado, números de usuários, volume de vendas, tempo economizado, quantidade de chamados, disponibilidade, métricas de performance ou tamanho de equipe. Não inventar métricas; criar uma lista de perguntas para recuperar esses dados com ex-colegas/clientes ou logs próprios.
- Não está documentado publicamente o escopo exato do trabalho de freelancer, os clientes autorizados a serem citados ou quais partes do sistema hospitalar podem ser mostradas. Usar descrições anonimizadas quando necessário.

## 2. Formação, stack e competências de DevOps

### Takeaway

Mostrar a formação como base, mas deixar a prova prática ocupar o centro: projetos, decisões técnicas e operação. A stack deve ser agrupada por função e nível de evidência, distinguindo “uso profissional”, “projetos publicados” e “em aprendizado” para evitar que uma lista longa pareça uma promessa de domínio uniforme.

### Cited Findings

- O GitHub sugere que o README de perfil inclua introdução, skills, experiência profissional e alguns projetos relevantes, além de conquistas ou certificações. — [GitHub Docs: Using your GitHub profile to enhance your resume](https://docs.github.com/en/account-and-profile/tutorials/using-your-github-profile-to-enhance-your-resume)
- O GitHub recomenda README em todo repositório para explicar e facilitar a navegação do trabalho; suas orientações de perfil também destacam descrição, demo, setup, exemplos e testes. — [GitHub Docs: Best practices for repositories](https://docs.github.com/en/repositories/creating-and-managing-repositories/best-practices-for-repositories); [GitHub Docs: Using your GitHub profile to enhance your resume](https://docs.github.com/en/account-and-profile/tutorials/using-your-github-profile-to-enhance-your-resume)
- O Google recomenda que um README explique para que serve o pacote, como usá-lo, a documentação relacionada e seu status; isso reforça que “stack” deve ser acompanhada de contexto de uso. — [Google Style Guides: READMEs](https://google.github.io/styleguide/docguide/READMEs.html)
- O conteúdo local informa formação em Análise e Desenvolvimento de Sistemas na UNIP (2022–2023) e Técnico em Informática no Colégio Univap (2019–2021), além de PHP/Laravel, React, Vue.js, Next.js, TypeScript, APIs REST, MySQL, Docker, CI/CD, VPS e Git. — [Base local consultada: `index.html`](../../index.html)
- O conteúdo local também associa Laravel, React/Vue, Docker e APIs às experiências/projetos, e descreve o trabalho de suporte com Active Directory, sistema MV e automação. — [Base local consultada: `index.html`](../../index.html)

### Inferences

- Estrutura recomendada para a seção “Como trabalho”: “Backend: PHP/Laravel, APIs REST”; “Frontend: React, Vue.js, TypeScript, Next.js”; “Dados: MySQL”; “Entrega: Docker, CI/CD, VPS, Git”; “Operação: Active Directory, suporte e automação”. A ordem deve refletir o alvo profissional, não a quantidade de itens.
- Marcar evidência sem usar barras de proficiência artificiais: “produção”, “projetos publicados”, “experiência operacional” e “estudando”. Exemplo: Laravel — produção/projetos; React/TypeScript — projetos; Docker/CI/CD/VPS — declarar somente junto a um projeto ou pipeline demonstrável.
- Na formação, incluir instituição, curso e datas em uma linha; acrescentar 1 frase sobre o que é relevante para a vaga. O TCC pode ser um caso de produto, pois o conteúdo local atribui a Giovane atuação como Product Owner e dev web no Alpha System.
- Recomenda-se uma “prova de DevOps” pequena e concreta no GitHub: README com arquitetura/deploy, `docker compose`, variáveis de ambiente exemplificadas sem segredos, workflow de CI, instruções de teste e uma seção “limitações/conhecidos”. Isso demonstra prática sem alegar senioridade em infraestrutura.
- Segurança é parte da apresentação profissional: GitHub recomenda Dependabot, secret scanning, push protection e code scanning para repositórios públicos. — [GitHub Docs: Best practices for repositories](https://docs.github.com/en/repositories/creating-and-managing-repositories/best-practices-for-repositories)

### Gaps

- O material local não mostra quais projetos têm Docker, CI/CD ou VPS configurados, nem quais provedores, workflows, testes ou monitoramento são usados. A recomendação deve ser “mostrar evidência” e não “afirmar domínio de DevOps”.
- Não há certificações informadas. Não adicionar certificações, níveis (“avançado”) ou ferramentas cloud sem prova verificável.

## 3. Estudos de caso e copy concisa em português

### Takeaway

Usar 2–3 estudos de caso profundos, não seis descrições equivalentes. Cada caso deve responder rapidamente: problema, público/contexto, papel de Giovane, decisão técnica, resultado comprovado, link de demonstração/código e o que ainda não está disponível para divulgação.

### Cited Findings

- A orientação de currículo da Harvard alerta contra linguagem passiva, falta de resultados, desorganização e texto pouco escaneável; recomenda verbos de ação, impacto, consistência e leitura fácil. — [Harvard FAS: Create impactful resumes and cover letters](https://careerservices.fas.harvard.edu/resources/hes-create-impactful-resumes-and-cover-letters/)
- A Nielsen Norman Group recomenda conteúdo objetivo, sem exagero promocional, com títulos, listas e trechos curtos para facilitar a varredura visual. — [Nielsen Norman Group: Concise, Scannable, and Objective](https://www.nngroup.com/articles/concise-scannable-and-objective-how-to-write-for-the-web/)
- Em entrevistas com profissionais de UX, a Nielsen Norman Group relata que gestores valorizam evidência de decisões, escrita clara e ligação entre trabalho e resultados de usuário/negócio; também observa que portfólio nem sempre é obrigatório, especialmente para vagas juniores ou não visuais. A inferência aplicável a full-stack é priorizar evidência técnica e de produto, sem transformar o portfólio em peça visual vazia. — [Nielsen Norman Group: User Experience Careers, 2nd edition](https://media.nngroup.com/media/reports/free/UserExperienceCareers_2nd_Edition.pdf)
- O conteúdo local lista Petti PDV (vendas, estoque, clientes e caixa; Laravel/Vue/MySQL), Sistema de Gestão 3.0 (backend refeito e interface nova; Laravel/React/TypeScript/Electron), Alpha System Web (API Laravel + Next.js/Material UI para folha de pagamento), API de Clientes, Campos Dinâmicos e TCC Alpha System. — [Base local consultada: `index.html`](../../index.html)
- A homepage pública do Petti está vinculada ao projeto no portfólio. — [Petti](https://petti.tech/)

### Inferences

- Caso principal recomendado: **Petti PDV**. Ele combina produto real, domínio de negócio e stack coerente. Estrutura sugerida: “Contexto: operação de lojas de ração”; “Meu papel: desenvolvimento full-stack”; “Problema: centralizar vendas, estoque, clientes e caixa”; “Decisões: Laravel, Vue.js, MySQL”; “Resultado: sistema publicado em [petti.tech](https://petti.tech/)”; “Evidência: screenshots, fluxo de venda e limitações”. Só incluir números de lojas/usuários se Giovane puder comprová-los.
- Segundo caso: **Sistema de Gestão 3.0**. O foco deve ser a decisão de refazer backend e interface, explicar por que React/TypeScript/Electron foram usados e mostrar o que Giovane implementou. A frase “interface do zero com foco em UX” deve virar descrição de decisões observáveis: fluxos, componentes, validações ou problemas de usabilidade resolvidos.
- Terceiro caso: **Alpha System**. O papel de Product Owner é um diferencial, mas deve ser delimitado: “organizei backlog/roadmap e atuei no desenvolvimento”, se isso corresponder ao trabalho real. Separar claramente autoria individual, trabalho de equipe e partes acadêmicas.
- Copy recomendada para a abertura: “Desenvolvedor full-stack brasileiro. Construo aplicações web, APIs e sistemas administrativos com Laravel, React/Vue e TypeScript — do problema ao deploy.” É curta, contém termos pesquisáveis e não promete “escalabilidade” sem prova.
- Copy recomendada para experiência: “Desenvolvi e coloquei em produção um ERP/PDV para vendas, estoque, clientes e caixa, usando Laravel, Vue.js e MySQL.” Usar “coloquei em produção” apenas porque o conteúdo local afirma produção real; revisar se a autoria foi individual ou compartilhada.
- Evitar: “código limpo, arquitetura sólida, performance e escalabilidade” como afirmações isoladas. Preferir: “organizei X”, “integrei Y”, “automatizei Z”, “documentei A”, sempre com evidência ou com qualificador (“buscando”, “com foco em”).

### Gaps

- Não há dados públicos suficientes para escrever resultados quantitativos dos três casos. Faltam métricas, decisões registradas, trade-offs, testes, arquitetura, screenshots atualizados e relatos de usuários.
- O link público do Petti foi confirmado como existente na página, mas a ferramenta de pesquisa não expôs seu conteúdo textual; revisar manualmente demo, acessibilidade, estado atual e autorização para divulgar detalhes.

## 4. GitHub, links de projetos e plano editorial

### Takeaway

O portfólio deve funcionar como índice: a home apresenta posicionamento e 2–3 casos; o GitHub fornece a prova técnica; demos mostram produto. O perfil de Giovane deve fixar até seis itens, priorizando 3–5 projetos relevantes e bem documentados, em vez de tentar destacar tudo.

### Cited Findings

- O GitHub recomenda destacar 3–5 projetos relevantes e diversos, combinando projetos próprios e contribuições quando possível; gestores podem olhar os projetos por apenas alguns minutos. — [GitHub Docs: Using your GitHub profile to enhance your resume](https://docs.github.com/en/account-and-profile/tutorials/using-your-github-profile-to-enhance-your-resume)
- O GitHub permite fixar até seis repositórios/gists e reordená-los, para que os melhores trabalhos apareçam rapidamente no perfil. — [GitHub Docs: Pinning items to your profile](https://docs.github.com/en/account-and-profile/how-tos/profile-customization/pinning-items-to-your-profile)
- Para cada projeto destacado, o GitHub recomenda descrição curta, site/demo, tópicos, features, setup, exemplo/demo e testes; também recomenda código legível e dependências atualizadas. — [GitHub Docs: Using your GitHub profile to enhance your resume](https://docs.github.com/en/account-and-profile/tutorials/using-your-github-profile-to-enhance-your-resume)
- O Google recomenda README atualizado no topo do repositório, com finalidade, status, uso e documentação relacionada. — [Google Style Guides: READMEs](https://google.github.io/styleguide/docguide/READMEs.html)
- Links atualmente apresentados no conteúdo local: [perfil GitHub de Giovane](https://github.com/giovane-breno), [Alpha System Web](https://github.com/giovane-breno/alpha-system-web), [API de Clientes](https://github.com/giovane-breno/customer_management), [TCC Alpha System](https://github.com/giovane-breno/ALPHA-SYSTEM), [Campos Dinâmicos em Laravel](https://github.com/giovane-breno/Dynamic-Form-Fields-in-Laravel) e [Petti](https://petti.tech/). — [Base local consultada: `index.html`](../../index.html)

### Inferences

- Ordem sugerida de pins: 1) Petti ou repositório/documentação do Petti, se puder ser público; 2) Sistema de Gestão 3.0, se houver repositório/demonstração; 3) Alpha System Web; 4) TCC Alpha System; 5) API de Clientes; 6) Campos Dinâmicos. A ordem deve mudar conforme a vaga: backend prioriza APIs/Laravel; full-stack prioriza Petti e Gestão 3.0; produto prioriza Alpha System.
- Cada README deve começar com uma frase em português e, se a busca for internacional, uma versão curta em inglês. Template mínimo: “O que é”; “Meu papel”; “Stack”; “Demo”; “Como executar”; “Testes”; “Arquitetura/decisões”; “Limitações”; “Status”. Não usar badges decorativos sem workflow ou licença que os sustente.
- Os links de “Ver projeto” e “Repositório” precisam ser rotulados pelo próximo passo: “Abrir demo”, “Ver código”, “Ler estudo de caso” ou “Ver API/documentação”. Isso reduz ambiguidade e deixa a navegação escaneável.
- Antes de publicar, testar todos os links, remover segredos, adicionar `.env.example`, confirmar licença e indicar se um repositório é acadêmico, demonstração ou produção. Se o código de cliente não puder ser aberto, publicar uma versão sanitizada, screenshots autorizados ou um estudo técnico sem dados sensíveis.
- Checklist editorial mensal: uma frase de posicionamento; datas consistentes; três casos com evidência; README dos pins; demo funcional; stack agrupada; claims classificados como comprovados ou a validar; copy sem “especialista”, “sênior”, “escalável” ou “alta performance” sem prova.

### Gaps

- Não foi possível verificar, apenas pela pesquisa textual, se os quatro repositórios estão públicos, executáveis, atualizados, licenciados ou com README suficiente. Isso deve ser auditado antes de prometer “código disponível”.
- Não há LinkedIn, currículo PDF ou e-mail de contato verificados nas fontes públicas consultadas; manter esses canais consistentes com o domínio e o GitHub antes de divulgar o portfólio.
